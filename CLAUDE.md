# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A small, single-user GTD web app (Flask + Jinja + stdlib `sqlite3`). It replaced Mindwtr, which had
grown too complicated. Keep it simple: prefer the plain GTD workflow over options and settings.
The phone is only for capture; everything else is done on a desktop, so features need no touch or phone adaptation.

**Keep this file current.** Update it in the same change whenever any of these change:
- a command or environment variable
- the architecture
- a GTD rule built into the code
- the test setup

Delete anything here that has become wrong.

## Commands

```bash
GTD                                             # open the live app: https://home.<tailnet>.ts.net (GTD_URL to override)
GTD dev                                         # pull a fresh snapshot of live data into dev.db, run locally, open http://127.0.0.1:5005
GTD dev --keep                                  # same, reusing the existing dev.db
git push home main                              # deploy (after tests pass); also push origin
uv run app.py                                   # bare dev server (GTD_HOST / GTD_PORT to override)
uv run pytest                                   # all but the browser tests, in parallel (-n auto in pyproject.toml; ~3s)
uv run pytest -m ""                             # everything, browser tests included (~12s)
uv run pytest -m browser                        # browser tests only (real Chromium, ~10s)
uv run pytest -n0 tests/test_app.py::test_horizons  # one test (-n0 skips starting the parallel workers)
uv run pytest -n0 -k calendar                   # by keyword
```

Env vars:
- `GTD_DB` points to the SQLite file. Default: `gtd.db` next to the code. On the VM it is `/var/lib/apps/gtd/gtd.db`; `GTD dev` sets it to `dev.db`. `gtd.db*` and `dev.db*` are gitignored (the repo is public).
- `GTD_SECRET` sets the Flask session key used for flash messages.
- `GTD_DEBUG=1` turns on Flask's debug mode and auto-reload.
- `GTD_URL` overrides the live URL `GTD` opens. On the VM it is also the address a reminder's tap opens (`Click`); unset, a reminder has no link.
- `GTD_CALENDARS` lists external calendars shown read-only on the calendar: whitespace-separated `name=ics-url` pairs (`_` in a name is a space; `webcal://` reads as `https://`). Google's "secret address in iCal format", Outlook's published ICS link. Secret: only in the VM's env file. Unset: none.
- `NTFY_URL` is the ntfy topic reminders are POSTed to (on the VM `http://127.0.0.1:5007/gtd`). Unset (dev, tests): no reminder thread, nothing is sent.

There is no build step, linter config or JS bundler.

`GTD dev` restarts a running local server when any `*.py`, template or static file is newer than `.server-started`, which it touches on every start. A server it didn't start counts as stale.

## Hosting and development

The app runs on `home`, a GCP free-tier e2-micro (us-east1) reached only over Tailscale; it holds the only live copy of the DB. VM-wide setup (systemd `app@.service`, deploy hook, nightly backups, port table) lives in `~/Github/personal/GCP-home-server`, not here; `deploy/gtd.env.example` is this app's `/etc/apps/gtd.env`. It runs as `gunicorn -w 1 --threads 4` (one worker keeps the timer and SQLite simple); `connect()` sets WAL and a 5 s busy timeout.
- Develop on the Mac only, with `GTD dev`. Never point a local server at the live DB. Don't develop on the VM (its 1 GB RAM is for the apps).
- Deploy with `git push home main` once tests pass. The hook backs up the DB (`/var/lib/apps/gtd/backups/gtd-predeploy-*.db`), checks out, `uv sync`s and restarts; a failed start prints the journal in the push output.
- There are no migrations: `SCHEMA` (`CREATE ... IF NOT EXISTS`) only adds what's missing. A change it can't make (a new column on an existing table, a changed `CHECK`) needs a one-off step: run it by hand on the VM (after a backup), check it first on `GTD dev`, and don't keep it in the code.
- Rollback: `git push -f home <good-sha>:main`; if a schema change damaged data, also restore the pre-deploy backup. A backup from before a schema change needs the code of its day.
- The VM's timezone is America/New_York (and `TZ` in the env file): `today()` and the timer's local times use the server's zone.

## Architecture

- **`db.py`** holds the schema and every query.
  - `connect()` runs `SCHEMA` (`CREATE ... IF NOT EXISTS`) once per file: it then stores `SCHEMA_VERSION` (a CRC of `SCHEMA`) in `PRAGMA user_version` and later connections skip it until `SCHEMA` changes. So schema changes must stay idempotent. Seed rows use `INSERT ... WHERE NOT EXISTS`.
  - SQLite can't alter a `CHECK`, so changing one needs a table rebuild, run with foreign keys off: dropping `projects` would null every task's `project_id`, and dropping `tasks` would cascade away the time entries.
  - The live DB still has an unused `projects.updated_at` column (dropped from `SCHEMA` on 2026-10-30); harmless.
  - **Transactions:** every public write function is `@atomic` (`transaction()`): its writes commit together or not at all, and nested calls join the outermost one, which alone commits. Helpers never call `commit()`. A route that does several writes as one action wraps them in `with db.transaction(c):` (a task moved to Reference, a status change with its tickler date).
  - Writes go through `_insert`/`_update`, which whitelist columns (`TASK_FIELDS`, `PROJECT_FIELDS`, `HORIZON_FIELDS`) and raise on unknown fields.
  - Rows are `sqlite3.Row`.
- **`app.py`** holds the Flask routes.
  - No login, so `same_origin_only()` refuses a POST whose `Sec-Fetch-Site` is anything but `same-origin` or `none` (CSRF from another site's page). Clients that aren't browsers (ntfy's buttons) don't send the header and pass.
  - Uses one connection per request (`g.db`).
  - `today()` reads `app.config["TODAY"]`, which lets tests pin the date. Never call `date.today()` directly.
  - A context processor injects `counts`, `today` and the running `timer` into every template.
  - `task_fields_from_form()` is the single place that turns form input into task fields; it validates the repeat rule.
- **`recur.py`** is pure date math.
  - Rules are `daily|weekly|monthly|yearly` or `every N day|week|month|year(s)`.
  - Both step from their anchor by `n*k`, so month-end days don't drift.
  - `next_due()` returns the first such date after today, stepping from the old due date.
  - A rule ending in `after done` or `after completion` (e.g. `every 2 weeks after done`, `weekly after done`) counts from the completion date: `next_due()` steps from today.
- **`dates.py`** is pure date parsing (`parse(text, today)`): ISO, `today|tomorrow|yesterday`, weekdays (always the next one after today), `next week|month`, `in N days|weeks|months`, `oct 30`, month-first numbers (`4/15`, `04-15-2027`, `4/15/27`; no year means the next one).
  - `task_fields_from_form()` runs every `due_date` through it, so the task page and the add lines take words. Their `date_input()` macro (`_task.html`) is a text box plus a 📅 button; the button opens a hidden native `<input type="date">` and the JS in `static/app.js` copies the pick into the text box (on a touch screen, `(pointer: coarse)`, that input lies invisibly over the button instead, since iPad Safari doesn't always open `showPicker()`) (and fires `change`, so a task page saves it; while the picker is open the box is `.picking` and waits). The task page's Remind box uses it too, with `type='datetime-local'` (date and time; the pick lands as `YYYY-MM-DD HH:MM` and updates the preview). An unparseable date is flashed and ignored. The calendar's add form keeps its native date picker.
  - **Live previews:** on the task page, a `.hint.when` beside the Due, Repeats and Remind boxes shows how each reads as you type (`→ Fri Oct 23`, `→ every 2 weeks · next Fri Nov 6`, `not understood`), from `/parse/<kind>` (`due|recur|remind`, `parse_preview()` in `app.py`; one loop in `static/app.js`). The Repeats hint gives the rule in words (`describe_recur()`) and the date completing it would set (`recur.next_due()` from the Due box, or today; an `after done` rule adds "if done today"), and follows edits to the Due box too. Due and Repeats show their saved value's reading on load.
- **New items go to the top** of every list they arrive in: tasks arriving in Inbox, Next, Waiting or Someday get a top list position, project steps and projects a top position (below); calendar days break due-date ties newest first. Reference stays alphabetical; goals and areas are dragged (below).
- **Done** (`/done`, `db.done_tasks()`) lists only what was closed in the last `DONE_DAYS` (7) local days, today included (`since=`; older items stay findable by search and on their project's page), a repeat's done instances once, the latest (`once=True`). Done projects (`db.closed_projects()`) and tasks fold into two `details.band`s (`done_bands` filter in `app.py`: Today, Past week; projects first, newest first), remembered like Next's; then Abandoned's projects and tasks (`state="abandoned"`); every row has Revive (`closed_project()` in `_task.html` for projects). The steps a closed project took down with it aren't listed one by one there; its page lists them.
  - A project page lists its abandoned steps under Abandoned, below Completed and with it (`completed(abandoned=True)`, `_done_toggle.html`), each with Revive. Abandoned rows show ✕ and a Revive button. There is no separate archive tab.
  - A "Show completed" toggle (`?done=1`, `completed()` in `app.py`, `_done_toggle.html`) does the same on Next (every done task), and a project page (that project's steps); hidden by default everywhere; Active projects lists done and abandoned projects, with Revive. Done rows show a ✓, the completion date and Revive instead of a tick-off button, so a done repeating task can't be completed twice.
- **Calendar** (`/calendar`) shows a month (`?m=YYYY-MM`) or one week (`?w=<any date>`, Sunday-first; the Timer's week totals still start Monday); the Month/Week buttons switch. Each task shows once, on its due date: a repeat's future dates aren't projected. A bare `/calendar` (the nav link) opens the view last used, kept in the `cal_view` cookie, on today's month or week.
  - Each task has a colored left stripe and tint by kind (`k-next|later|waiting|someday|inbox`; an inbox item wins, then a someday project or task, then waiting task or project, else the status), with a dot legend below the grid.
  - The header's actions are `‹ Today ›` and a Month|Week toggle. Clicking a day number opens the add dialog on that day (`.day-dialog`, the add line's fields; it posts as the line does, so the page reloads where it was).
  - A press beside a task selects nothing (`selectstart`; `user-select: none` here would stop the tasks dragging). Dragging a task onto another day moves its due date (`/tasks/<id>/due`, 204 for fetch); the JS in `calendar.html` moves it in place, so the page doesn't reload. Only open tasks move.
  - The crawler follows calendar links only within `CALENDAR_MONTHS`.
  - **External calendars** (`extcal.py`, `GTD_CALENDARS`): read-only ICS feeds (`icalendar` + `recurring-ical-events`, which expands repeats). Fetched on first use, then refreshed in a background thread once older than `FRESH` (15 min; `RETRY` 1 min after a failure), so a page waits only the first time; a failed feed keeps its last good copy and shows ⚠ (the error as tooltip) by its legend name. Events (`span.ev.ext`, stripe `x-<feed index % 3>`, no tint, muted) sit above the day's tasks: all-day first, then by local start time; a multi-day one shows on each day, its time on the first. Cancelled ones are left out. No click, no drag; the tooltip gives calendar, time and place. They're calendar-only: not on Next, the review or the nav dots.
- **Timestamps** (`created_at`, `completed_at`) are SQLite `datetime('now')`, i.e. UTC. Show their date with the `local_date` filter, never `[:10]`, or an evening's work shows as tomorrow.
- **Same kind, same behavior** (a soft rule for every change): every object of a kind behaves the same wherever it appears. Every record (task, project, horizon, reference item) opens the same way (its overlay), every task list sorts, drags, ticks and files the same way, every project page and project list works alike. A new feature for one task list or one record page goes to all of its kind, or needs a reason.

Keep it lean and uniform: every page has the same layout, built from the same parts, so no page needs its own reading.

Timer, Calendar (minute-by-minute work); Inbox, Next, Waiting, Someday (tasks only); a muted "Projects" caption (`.caption`), then Active, Waiting, Someday (projects only: `projects_view(status)` at `/projects`, `/projects/waiting`, `/projects/someday`). Review, Horizons, Done (the weekly-review pages) and Reference sit muted on the right in `nav .aux`, then ◐ (theme), so it's reachable wherever the nav is.

## GTD rules encoded in the code

- **A task has a state and, inside a project or H0, a step.** There is no task "status".
  - `tasks.state` is `open | done | abandoned`; every open-task query says `state = 'open'` and never looks at `step` for that.
  - `tasks.step` is `next | waiting | later` for a project's task, `next | waiting | someday` for an H0 task, and `NULL` exactly for inbox items. `later` means a project step that isn't the next action yet. Beware SQL's `NULL`: `step != 'later'` skips every inbox item.
  - The schema enforces it: `CHECK ((step IS NULL) = (project_id IS NULL AND NOT ground))`, no `later` H0 task, no `someday` project task, and no H0 task in a project (the live DB was rebuilt for these on 2026-10-30, and for `someday` on 2026-10-31). `_fit_step()` (run by `add_task`/`update_task`) drops a step given to an inbox item; gives an H0 task `next` unless told or already `waiting` or `someday` (a `later` arriving is `next`); and takes a task joining a project out of H0 and makes it a `later` step unless a step is given or it was waiting (a `someday` given or held becomes `later`), so an H0 next action doesn't become the project's next by moving. `task_view()` drops the posted step when the project changed and the step select didn't, so a move from the task page lands the same way.
  - Writes reject unknown fields (`_insert` as well as `_update`), so a stray `status=` raises.
- **The inbox is not a step or a state.** It is every open task with neither a project nor H0, "ground level" (`tasks.ground`): `INBOX` in `db.py`, `db.inbox_tasks()`, and an `inbox` column on every `TASK_SELECT` row. Only H0 is a deliberate choice of no project; any other projectless task is an orphan, and orphans are the inbox.
  - Filing by drag: see "Moving tasks by drag" below; Inbox is one of its lists.
  - Completing an inbox item leaves it as it was (no project, not H0), as abandoning does, so a revive puts it back in the inbox; the Timer counts its time as "(no project)".
  - There is no Process page (removed 2026-10-27): the Inbox page is where items get dealt with (drag to file, ✓, or open one and pick its project). The Process walkthrough (Allen's flowchart in an overlay) was removed on 2026-11-04: multiple next actions and the split between tasks and projects left its questions behind. Don't add a second page doing the same.
  - The task page shows the step picker for open project and H0 tasks (H0: next, waiting, someday), not for an inbox item. `orphaned()` in `app.py` flashes when a task lands in the inbox.
- **H0 tasks are next actions, waiting or someday** (`step`): H0 next actions are on Next with the projects' (the H0 tab was merged into Next on 2026-10-31, once areas no longer set them apart); H0's waiting tasks are on Waiting, the delegated single actions no project needs; its someday tasks are on Someday, the single ideas not committed to.
  - **H0 tasks need no due date** (the always-dated rule of 2026-10-30 was dropped on 2026-10-31): undated ones fall in Next's No date band and aren't in its count. A someday one's date is its tickler (`_fit_step()` uses `today=` only for that).
  - H0 is the `h0` option in the `project_select()` macro, so choosing a project and choosing H0 are one decision. Its "＋ New…" option reveals a `new_project` box; `task_fields_from_form()` creates an active project from it and uses it, overriding the dropdown. A repeat rule doesn't exempt a task.
  - H0 next actions are also listed on the Horizons page's ground card (`db.h0_actions()`, `H0_NEXT`); their rows show an H0 tag where a project's link would be.
  - The task form and the calendar's add line send a task with neither a project nor H0 (the blank `project…`) to the inbox.
  - The calendar's add line (`add_next_action()` in `app.py`) adds a next action directly, beside any its project has.
- **Weekly review** (`/review`) is a checklist you finish, in Allen's order: get clear (collect loose ends, inbox to zero, mind sweep), get current (overdue, next actions, look ahead, waiting, projects, checklists), get creative (someday / maybe, new ideas), then horizons.
  - Its steps are `REVIEW_STEPS` in `app.py`, one card each in `review.html`. Each card's hint says in a sentence or two what to do there (with Horizons' guides, the exceptions to lean pages' few-word hints).
  - Projects lists every active and waiting project, flagged (⚠) first, then least recently reviewed, each with its outcome (→), every next action under it, and a ✓ (`/projects/<id>/reviewed`); its count is how many weren't looked at in the last week (`unseen()`), as for someday. Checklists links Reference items holding a checklist. New ideas has the page's add line (Someday's, plus item or project), above the deck as on Horizons; `back()` keeps you on the review. A tick posts to `/review/<step>` (ticking again unticks) and is stored in `review_checks`, so a half-done review survives a closed tab.
  - One card shows at a time (a deck, `ol.deck`): `?step=`, else the first unticked. The time is in tables of their own, `project_reviews` and `task_reviews` (no ALTER on the live DB), read as `reviewed_at` (with `tickle_on`) by `db.projects()`/`get_project()` and `db.someday_tasks()`. Someday projects' rows show it faintly (`ago` filter: today, 3d ago, 2w ago, 4mo ago, never).
- **Project statuses:** `active | waiting | someday | done | abandoned`. As statuses, someday and waiting are projects' only (a task is waiting or someday by its step). **Done and abandoned are the same but for the name** (`CLOSED` in `db.py`), as for tasks.
  - A project page's status is one select (active, waiting, someday, done, abandoned) that saves on pick (`project_view()`, `PROJECT_STATUSES` for the open ones). Picking done or abandoned (`db.close_project()`) closes a project from any open status: it and its open steps get that state with one shared `completed_at` (to the millisecond), a repeat spawns no next instance, its timer is stopped, its time kept. It leaves every list and picker (a task page of its step keeps it selectable through `project_select(keep=)`), and its page's select shows its state.
  - Revive (Done's or Active projects' button, `/projects/<id>/revive`, or picking an open status on its page; `db.revive_project()`) brings it back as someday, then the picked status, its steps that share that `completed_at` as `later` steps; one closed on its own before stays closed. Reviving (or adding) one step of a closed project also brings it back as someday (`_reopen_project()`).
  - A task page links up to its project (an H0 task has no such link) and can move the whole project to someday from there.
- **At least one next action per project, as many as are truly doable now** (Allen's rule; one per project until 2026-10-31). Making one next never demotes another; Make later (or the step picker) does.
  - When a project's last next action is finished, nothing is promoted automatically and nothing navigates: the project shows as stalled (⚠) until you pick one with "Make next" on its page.
  - ✓→ (on a project step's task page only; `/tasks/<id>/done-then-project`, `complete_then_project()` in `app.py`) completes the step and opens its project, so you can pick the next one right away. It's the plain ✓ plus a deliberate jump; a task without a project (a stale frame) opens its list with it open (`task_home()`).
  - **`next` is always a conscious choice, never a default.** A step added on a project page defaults to `later` (its step picker preselects it), even when the project has no next action, and so does filing an inbox item. Only Make next, the step picker, or the calendar's add line (above) set `next`.
  - An active project with no `next` task is "stalled": the `stalled` column of every project row (`PROJECT_SELECT` in `db.py`). An active or waiting (committed) project with no desired outcome is `vague`; a someday one needs none. Either shows ⚠, from the `warning` column (its tooltip: "No next action", "No desired outcome", or both); templates read it, never recompute it.
- **Desired outcome:** every active or waiting project states what done looks like, in `project_outcomes` (a table of its own, like `project_tickles`; `db.set_project_outcome()`, blank clears it), read as `outcome` by `PROJECT_SELECT`. Not required at creation (projects are made mid-flow); a missing one is ⚠ until filled.
  - On the project page it's the title's subtitle (`.title-line.outcome`, placeholder "Done when…", muted, no box until hovered), saved on change (`data-submit`, `project_view()`).
  - Its ✓ (an active or waiting project with an outcome) closes the project: with no open steps at once; else a native `popover` asks: Mark done / Abandon (its open steps) / Not yet. Both post to `/projects/<id>/reached` (`db.close_project()` with `steps`): the project is done, its open steps get the state picked.
  - Tasks of waiting and someday projects stay off Next Actions (`VISIBLE_NEXT`).
- **Waiting** (`/waiting`, `waiting.html`) holds waiting tasks only, H0's and project steps (a waiting step of a someday or done project too) in one dragged order. Waiting projects are on their own tab (`/projects/waiting`, ▸ and Expand all, dragged to reorder via `/projects/order/waiting`).
- **Contexts are tasks' only, and never asked for.** (Removed on 2026-10-23 because having to pick one slowed processing; back on 2026-11-04 as optional tags.) Nothing requires one. Tables `contexts` (`name` unique, case-insensitive; `position`) and `task_contexts`; a task has any number, read as `contexts` (names joined by a space) on every `TASK_COLS` row. A name is one word starting with a letter (`CONTEXT`; a box turns spaces into hyphens, `context_name()`). A context is made by first use (`db._context_id()`), on top of the list, and stays when its last task closes, until deleted. A repeat's next instance keeps them.
  - **Adding:** a `@home` title mark (`split_title()`, repeatable; `@5km`, `@/notes`, `call @home about taxes` stay titles, flashed), with @ offering the existing names (`app.js`: ↑↓, Tab or Enter takes one, Esc leaves it; on lines showing the marks' hint and task pages' titles, from `body[data-contexts]`). On an existing task's title only @ works: `app.js` peels it off once the title is left or on Enter, not on autosave's pause, so a half-typed name makes no context; or the task page's picker (`context_picker()` in `_task.html`, a form of its own below the task form, `/tasks/<id>/contexts`): each context a word one click turns on, saved in the background, plus a box for a new one.
  - **The filter** is global: the ticks in Site info, kept in the `contexts` cookie (ids joined by `-`, set by `app.js`), applied at once: `applyFilter()` fetches the page and swaps each `[data-filtered]` part (chip, list, calendar days, tickled toggle) in place, under Site info, so nothing else repaints; several ticks mean any of them. Those lists' events are delegated, and their drop panel and File to button stay while a filter empties them (`tasks or context_filter`), so the rows it brings back work. `filtered()` in `app.py` applies it in `FILTERED_VIEWS` only: Next (Show completed too), Waiting, Someday, Calendar (not its external events). Not the Inbox (the landing place), project pages and tabs (repositories, not working places), the review, Horizons, Done, search or the nav's dots, which stay the whole truth.
  - Those four pages have `context_chip()` in their header: what's showing (click: Site info; its tooltip counts the hidden), × to clear. `[data-filtered]` marks a page the filter thins. A list it empties says "Nothing in this context." (`nothing_here()`), not the big ✓.
  - A task added on the Calendar while filtered takes the checked contexts (`stay_in_view()`, by the Referer), or it would vanish; a @mark wins, flashing if that hides it. Capture (so the task lists' add lines), the review's new ideas and project steps never take them.
  - Dragging a filtered list: `db.reorder_tasks()` gives the posted rows the places they hold in their whole list (`LIST_ORDER`), so hidden rows (and other bands of Next) don't move.
  - **Site info** (`?`, `.help-dialog`, three columns that wrap as the window narrows: contexts; shortcuts, title marks, bookmarklet; go-keys; focus starts on its heading, never a field, which would swallow the next key just after closing) lists them (`ul.context-list`, in `base.html`, no forms): drag to reorder (`/contexts/order`), tick to filter at once, name box saves when left (`/contexts/<id>/rename`, JSON; onto an existing name it `confirm()`s, then merges), ✕ `confirm()`s, then deletes (`/contexts/<id>/delete`; tasks stay). Rename or delete redraws the page on closing.
- **Areas (H2) are the spine of Horizons, linked only there.** A goal serves one area (`goal_areas`), a project hangs under one goal or one area (`project_horizons`), an H0 task under one area (`task_areas`), and each area has a vision line (`area_visions`, "In 3–5 years…"), from which H4 is built. One parent each (the child is the key): linking elsewhere moves it. Tables of their own, no ALTER; `db.set_goal_area()`, `link_project()`, `link_task()`, `set_area_vision()` raise `ValueError` on a wrong level (→ 400). Set only from a goal's or area's page (`horizon.html`: chips that open their record, × to unlink from here, a "＋ …" select to link, `/horizons/<id>/link`; a goal's "Serves …" select) and, for the vision line, only the purpose & vision card. Nothing else in the app shows or asks for them: no area picker or grouping on project or task pages (that friction is why projects lost their `area_id` on 2026-10-30). A repeat's next instance keeps its area; closing a project keeps its link (off the map until revived). An area's page (`/horizons/<id>`) is title, a balance slider, standard, notes and its links, deletable; a goal's Ctrl+↑ goes to its area.
  - **Balance:** how much attention an area gets against what it needs, -3 far too little, 0 balanced, 3 far too much (`BALANCE` in `app.py`; table `area_balance`, no row = not set, `db.set_area_balance()`, read as `balance` by `db.horizons()`/`get_horizon()`). The slider (`balance()` in `_balance.html`, `.balance`, not a form field) is on the area's page (with its scale) and in each area's row on H2's card (after a fixed name column, in place of its notes' first line); it shows its word as you drag and saves on release in the background (`/horizons/<id>/balance`, 204 for fetch; blank clears). Red-green-red track, green at balanced; faint when unsetinstead of its notes' first line. The live DB keeps an unused `projects.area_id` (nulled on deploy) and `horizons.archived_at`; harmless.
- **Next lists every next action** (`db.next_list()`, `NEXT`): H0's and active projects' (not waiting or someday projects'), repeats not yet due too, split into due bands, each in its dragged order (new arrivals on top).
  - The rows fold into due bands (`banded()` in `_task.html`, `BANDS`, `soon()` and the `bands` filter in `app.py`), each a `<details>` with a count: Now (overdue + today) open; This week, Later and No date folded. Empty bands aren't shown. `static/app.js` remembers a band you click open or folded, per page (`localStorage`, `fold:<path>:<band>`); only clicks are saved, since a band that starts open fires `toggle` too.
  - Dates and ↻ show on hover (an overdue date always).
- **A task row's project link follows its title** (`.name` in `row()`), so it doesn't float alone in the right-hand column once dates hide; the title has `flex-basis: 0`, so a long one wraps instead of pushing the buttons onto a line of their own.
- **Recurring tasks** keep their step (or H0), except a next step comes back as later (below), but don't count until their due date: the weekly review and `db.next_actions()` use `VISIBLE_NEXT`.
- **The Next nav count** shows only tasks due today or overdue (`DUE_NEXT`), so undated tasks and future repeats aren't in the number.
  - `complete_task()` marks the task done and inserts the next instance. A repeating `next` step's instance is a `later` step, so the project stalls until you pick its next action; waiting steps and H0 tasks (next or waiting) keep theirs.
  - A repeat rule without a due date gets today as its due date.
- **A closed project has no open tasks:** closing it closes them, and an open task joining it (a revived step, adding one) reopens it as someday (`_reopen_project()` in `add_task`/`update_task`/`revive_task`). Moving a project out of done or abandoned clears its `completed_at`.
- **Only an empty project can be deleted** (no tasks at all, done and abandoned ones included; `db.project_deletable()`). The project page shows ✕ only then.
- **Deleting a task abandons it** (`db.abandon_task()`: state `abandoned`, `completed_at` set, its timer stopped, its time kept).
  - **Done and abandoned are the same but for the name** (categorization only): both revive, both delete for good.
  - Revive (`/tasks/<id>/revive`, `db.revive_task()`; done or abandoned) brings it back where it was: a later step of its project (reopening the project if it's done), an H0 task (next or waiting, as it was), or the inbox.
  - Reviving a done repeat deletes the next instance its completion made, unless that has time on it.
  - Deleting a done or abandoned task is a hard delete (its time too).
  - Completing an abandoned task does nothing. Search and suggestions include abandoned tasks with the done ones.
- **Horizons** live in one table keyed by `level`:
  - Goals and areas are reordered by their ⠿ grip on their card (`/horizons/order/<level>`, `db.reorder_horizons()`), saved in `horizon_positions` (own table, no ALTER; no row sorts last, alphabetically); a new one goes on top.
  - `purpose` and `vision` are single seeded notes that can't be deleted.
  - `goal` and `area` are lists of notes.
  - A goal or area also has an outcome line under its title (`horizon_outcomes`, `db.set_horizon_outcome()`, read as `outcome` by `HORIZON_SELECT`; blank clears): “Done when…” for a goal, “Kept up when…” for an area. Saved on change like a project's (`data-submit`, `horizon_view()`); a goal's row on its card shows it (→) in place of the notes' first line. Purpose and vision have none.
  - `/horizons` lands on a map: `db.horizon_graph()` (`{nodes: [{id, kind, title, url, sub, warn, dim}], edges}`: purpose & vision (one node, as on their card) → each area → its goals, projects and H0 next/waiting actions; a goal → its projects; anything serving nothing has no edge up, "loose") embedded as JSON and drawn by `static/graph.js` alone, so another view (matrix, tree) can replace it without touching the server. The layout is deterministic (radial seed by area, a fixed number of force steps), so a reload draws the same map; purpose & vision is the fixed centre; nodes are grey, darker the higher the level, ⚠ amber; loose nodes float outside as dashed rings; hover lights a node's neighbours; a click opens its overlay (purpose & vision its card), drag moves a node, the background pans, the wheel zooms. Under it, `ul.levels`: a line per `HORIZON_STEPS` level, its swatch hiding it on the map (kept in `localStorage`, H0 hidden at first), its name opening the card. `?level=` opens that level's card (a crumb links back); titles in `HORIZON_TITLES`. The header's elevator buttons (`HORIZON_FLOORS`, `.floor`: H5 … H0, each labelled) go straight to a level, on the map too, where none is lit; the levels aren't a sequence, so no ‹ › or ← →. H5 and H4 share a card and light together; H4 lands on its part. Each card opens with a guide (`guides` in `horizons.html`): what the level is, numbered steps to work it, examples, and when to revisit it. Purpose (H5) and vision (H4) share one card, `purpose` (`HORIZON_STEPS`), two autosaved notes one above the other, each with its guide right under it (the vision's after its areas), then every area's vision line under "Area by area", each saved in the background as it's left (`form[data-background]`, `/horizons/<id>/vision`, `app.js`); goal and area cards get the page's add line; deleting a goal or area returns to its card.

## Tests

Every change must be verified before it is called done:
1. For a change in behavior (a GTD rule, a route, a query, date math, JS behavior), write or extend a test that fails without the change, and watch it fail first.
2. Run the whole suite (`uv run pytest`; with template or JS changes, `uv run pytest -m ""`).
3. Click through the real app (`GTD dev`) for anything visual.

Keep the suite from piling up:
- Prefer extending the existing test for a feature over adding a new one.
- Looks (CSS, spacing, wording, icons, layout) get checked by eye, not by a new test; the crawl already checks every page renders and keeps the skeleton.
- A browser test only for JS behavior the Flask client can't see; anything checkable in the HTML goes in `test_app.py` (milliseconds, not a Chromium page).
- When a feature is removed or changed, delete or rewrite its tests; don't add "X is gone" tests for it.

Enforcement:
- Tests run in parallel with pytest-xdist (`-n auto` in `pyproject.toml`'s `addopts`): one process per core, each with its own Chromium and live server for the browser tests. `test_every_form_submits`, the slowest, is split into `SHARDS` parts so they run side by side. Tests mustn't share state across files or depend on order.
- A Claude Code Stop hook (`.claude/settings.json` → `.claude/hooks/run-tests.sh`) won't let a turn end while tests fail. It also runs the browser tests (in the same run) when `templates/` or `static/` have uncommitted changes. After a green run it stores a fingerprint of the working tree (`.git/tests-green`) and skips the tests on a turn that changed nothing since.
- `.githooks/pre-commit` refuses commits while tests fail. It also runs the browser tests (in the same run) when the commit touches `templates/` or `static/`. It is enabled per clone with `git config core.hooksPath .githooks`.

Layout (Flask test client, temporary DB):
- `tests/conftest.py` holds the fixtures:
  - `client` pins `TODAY = 2026-10-22` and makes Jinja undefined variables raise errors, so a template typo fails instead of rendering blank.
  - `conn` opens a second connection to the same file, so assertions can go straight to `db.*`.
  - `seed(c)` builds one of everything the UI can show (each task status, H0 next and waiting, repeats, waiting/someday/done projects, H0 someday tasks plain (reviewed), tickled to today and to later, a tickled someday project, an active project with an outcome and one with neither outcome nor next action, a checklist in Reference, horizons linked up and down, with some projects and H0 actions left loose, contexts on open tasks and one on a closed task alone). Its ids are deterministic.
  - New date-dependent behavior should be tested against the fixed date.
  - External calendars are tested with `extcal.fetch` monkeypatched to return an ICS string, `extcal._feeds` reset, `app.config["CALENDARS"]` set, and the `new_york` fixture (`test_app.py`) pinning the local zone.
- `tests/test_app.py` holds the targeted tests: GTD rules, routes, recurrence, edge cases.
- `tests/test_browser.py` (marker `browser`, Playwright + Chromium, one live server per run on a random port, a freshly seeded DB per test) drives the JS: tick-off, search suggestions, theme toggle, capture dialog, dragging project steps, task-list rows and projects to reorder, the project rows' ▸ and Expand all, `/` and `f` keys, date picker, timer clock, timer entry autosave, the Markdown notes editor (rendering, saving, undo, toolbar, checklists), the Due, Repeats and Remind box previews, autosave and its conflict choices, the add line and "＋ New…" reveals, calendar day dialog and drag-to-reschedule, no text selected by a drag, dragging rows of every task list onto projects and someday (and a someday task onto H0), the record overlays (opening, Esc, reload only after a change, `/tasks/<id>` → `?project=…&task=`, stacking, Ctrl+↑, ‹ ›), ⌘/ capture and the backdrop click, a someday project's tickler box, the Horizons map (hover, swatches, click to open) and the Vision card's lines, the context filter, Site info's rename, delete and drag, the @ offer and the task page's picker, and fails on any JS error. One-time setup: `uv run playwright install chromium`.
- `tests/test_crawl.py` holds the generic tests. They usually catch accidental bugs before anyone writes a targeted test for them:
  - Every link reachable from `/` must load.
  - Every form, with each submit button and each `<select>` option, must submit and land on a 200 page. Each submission gets a fresh copy of the seeded DB and sends its own page as the Referer.
  - Saving any edit page without changing anything must leave the record unchanged.
  - Task rows must match what the tick-off script expects.
  - When you add a page, field, state or step, add it to `seed()` so the crawler reaches it.
