# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A small, single-user GTD web app (Flask + Jinja + stdlib `sqlite3`). It replaced Mindwtr, which had
grown too complicated. Keep it simple: prefer the plain GTD workflow over options and settings.
The phone is only for capture; everything else is done on a desktop, so features need no touch or phone adaptation.

**Keep this file current.** Update it in the same change whenever any of these change:
- a command or environment variable
- the architecture
- a GTD rule built into the code
- the test setup

Delete anything here that has become wrong.

## Commands

```bash
GTD                                             # open the live app: https://home.<tailnet>.ts.net (GTD_URL to override)
GTD dev                                         # pull a fresh snapshot of live data into dev.db, run locally, open http://127.0.0.1:5005
GTD dev --keep                                  # same, reusing the existing dev.db
git push home main                              # deploy (after tests pass); also push origin
uv run app.py                                   # bare dev server (GTD_HOST / GTD_PORT to override)
uv run pytest                                   # all but the browser tests, in parallel (-n auto in pyproject.toml; ~3s)
uv run pytest -m ""                             # everything, browser tests included (~12s)
uv run pytest -m browser                        # browser tests only (real Chromium, ~10s)
uv run pytest -n0 tests/test_app.py::test_horizons  # one test (-n0 skips starting the parallel workers)
uv run pytest -n0 -k calendar                   # by keyword
```

Env vars:
- `GTD_DB` points to the SQLite file. Default: `gtd.db` next to the code. On the VM it is `/var/lib/apps/gtd/gtd.db`; `GTD dev` sets it to `dev.db`. `gtd.db*` and `dev.db*` are gitignored (the repo is public).
- `GTD_SECRET` sets the Flask session key used for flash messages.
- `GTD_DEBUG=1` turns on Flask's debug mode and auto-reload.
- `GTD_URL` overrides the live URL `GTD` opens. On the VM it is also the address a reminder's tap opens (`Click`); unset, a reminder has no link.
- `NTFY_URL` is the ntfy topic reminders are POSTed to (on the VM `http://127.0.0.1:5007/gtd`). Unset (dev, tests): no reminder thread, nothing is sent.

There is no build step, linter config or JS bundler.

`GTD dev` restarts a running local server when any `*.py`, template or static file is newer than `.server-started`, which it touches on every start. A server it didn't start counts as stale.

## Hosting and development

The app runs on `home`, a GCP free-tier e2-micro (us-east1) reached only over Tailscale; it holds the only live copy of the DB. VM-wide setup (systemd `app@.service`, deploy hook, nightly backups, port table) lives in `~/Github/personal/GCP-home-server`, not here; `deploy/gtd.env.example` is this app's `/etc/apps/gtd.env`. It runs as `gunicorn -w 1 --threads 4` (one worker keeps the timer and SQLite simple); `connect()` sets WAL and a 5 s busy timeout.
- Develop on the Mac only, with `GTD dev`. Never point a local server at the live DB. Don't develop on the VM (its 1 GB RAM is for the apps).
- Deploy with `git push home main` once tests pass. The hook backs up the DB (`/var/lib/apps/gtd/backups/gtd-predeploy-*.db`), checks out, `uv sync`s and restarts; a failed start prints the journal in the push output.
- There are no migrations: `SCHEMA` (`CREATE ... IF NOT EXISTS`) only adds what's missing. A change it can't make (a new column on an existing table, a changed `CHECK`) needs a one-off step: run it by hand on the VM (after a backup), check it first on `GTD dev`, and don't keep it in the code.
- Rollback: `git push -f home <good-sha>:main`; if a schema change damaged data, also restore the pre-deploy backup. A backup from before a schema change needs the code of its day.
- The VM's timezone is America/New_York (and `TZ` in the env file): `today()` and the timer's local times use the server's zone.

## Architecture

- **`db.py`** holds the schema and every query.
  - `connect()` runs `SCHEMA` (`CREATE ... IF NOT EXISTS`) once per file: it then stores `SCHEMA_VERSION` (a CRC of `SCHEMA`) in `PRAGMA user_version` and later connections skip it until `SCHEMA` changes. So schema changes must stay idempotent. Seed rows use `INSERT ... WHERE NOT EXISTS`.
  - SQLite can't alter a `CHECK`, so changing one needs a table rebuild, run with foreign keys off: dropping `projects` would null every task's `project_id`, and dropping `tasks` would cascade away the time entries.
  - The live DB still has an unused `projects.updated_at` column (dropped from `SCHEMA` on 2026-10-30); harmless.
  - **Transactions:** every public write function is `@atomic` (`transaction()`): its writes commit together or not at all, and nested calls join the outermost one, which alone commits. Helpers never call `commit()`. A route that does several writes as one action wraps them in `with db.transaction(c):` (a task moved to Reference, a status change with its tickler date).
  - Writes go through `_insert`/`_update`, which whitelist columns (`TASK_FIELDS`, `PROJECT_FIELDS`, `HORIZON_FIELDS`) and raise on unknown fields.
  - Rows are `sqlite3.Row`.
- **`app.py`** holds the Flask routes.
  - No login, so `same_origin_only()` refuses a POST whose `Sec-Fetch-Site` is anything but `same-origin` or `none` (CSRF from another site's page). Clients that aren't browsers (ntfy's buttons) don't send the header and pass.
  - Uses one connection per request (`g.db`).
  - `today()` reads `app.config["TODAY"]`, which lets tests pin the date. Never call `date.today()` directly.
  - A context processor injects `counts`, `today` and the running `timer` into every template.
  - `task_fields_from_form()` is the single place that turns form input into task fields; it validates the repeat rule.
- **`recur.py`** is pure date math.
  - Rules are `daily|weekly|monthly|yearly` or `every N day|week|month|year(s)`.
  - Both step from their anchor by `n*k`, so month-end days don't drift.
  - `next_due()` returns the first such date after today, stepping from the old due date.
  - A rule ending in `after done` or `after completion` (e.g. `every 2 weeks after done`, `weekly after done`) counts from the completion date: `next_due()` steps from today.
- **`dates.py`** is pure date parsing (`parse(text, today)`): ISO, `today|tomorrow|yesterday`, weekdays (always the next one after today), `next week|month`, `in N days|weeks|months`, `oct 30`.
  - `task_fields_from_form()` runs every `due_date` through it, so the task page and the add lines take words. Their `date_input()` macro (`_task.html`) is a text box plus a 📅 button; the button opens a hidden native `<input type="date">` and the JS in `static/app.js` copies the pick into the text box (on a touch screen, `(pointer: coarse)`, that input lies invisibly over the button instead, since iPad Safari doesn't always open `showPicker()`) (and fires `change`, so a task page saves it; while the picker is open the box is `.picking` and waits). The task page's Remind box uses it too, with `type='datetime-local'` (date and time; the pick lands as `YYYY-MM-DD HH:MM` and updates the preview). An unparseable date is flashed and ignored. The calendar's add form keeps its native date picker.
  - **Live previews:** on the task page, a `.hint.when` beside the Due, Repeats and Remind boxes shows how each reads as you type (`→ Fri Oct 23`, `→ every 2 weeks · next Fri Nov 6`, `not understood`), from `/parse/<kind>` (`due|recur|remind`, `parse_preview()` in `app.py`; one loop in `static/app.js`). The Repeats hint gives the rule in words (`describe_recur()`) and the date completing it would set (`recur.next_due()` from the Due box, or today; an `after done` rule adds "if done today"), and follows edits to the Due box too. Due and Repeats show their saved value's reading on load.
- **New items go to the top** of every list they arrive in: Inbox, Waiting and Someday's tasks list newest first, Next and calendar days break due-date ties newest first, and project steps and projects get a top position (above). Reference and horizons stay alphabetical.
- **Done** (`/done`, `db.done_tasks()`) lists done projects, the latest 100 done tasks, and under Abandoned the latest 100 abandoned projects (`db.abandoned_projects()`) and tasks (`state="abandoned"`), newest first. An abandoned project's steps aren't listed one by one there; its page lists them.
  - A project page lists its abandoned steps under Abandoned, below Completed and with it (`completed(abandoned=True)`, `_done_toggle.html`), each with Revive. Abandoned rows show ✕ and a Revive button. There is no separate archive tab.
  - A "Show completed" toggle (`?done=1`, `completed()` in `app.py`, `_done_toggle.html`) does the same on Next (every done task), and a project page (that project's steps); hidden by default everywhere; Projects lists done projects. Done rows show a ✓ and the completion date instead of a tick-off button, so a done repeating task can't be completed twice.
- **Calendar** (`/calendar`) shows a month (`?m=YYYY-MM`) or one week (`?w=<any date>`, Sunday-first; the Timer's week totals still start Monday); the Month/Week buttons switch. Each task shows once, on its due date: a repeat's future dates aren't projected. A bare `/calendar` (the nav link) opens the view last used, kept in the `cal_view` cookie, on today's month or week.
  - Each task has a colored left stripe and tint by kind (`k-next|later|waiting|someday|inbox`; an inbox item wins, then a someday project or task, then waiting task or project, else the status), with a dot legend below the grid.
  - The header's actions are `‹ Today ›` and a Month|Week toggle. Clicking a day number sets the add line's date and placeholder.
  - Dragging a task onto another day moves its due date (`/tasks/<id>/due`, 204 for fetch); the JS in `calendar.html` moves it in place, so the page doesn't reload. Only open tasks move.
  - The crawler follows calendar links only within `CALENDAR_MONTHS`.
- **Timestamps** (`created_at`, `completed_at`) are SQLite `datetime('now')`, i.e. UTC. Show their date with the `local_date` filter, never `[:10]`, or an evening's work shows as tomorrow.

It stays whole (notes, repeat, reminder, time). To commit to one: drag it from Someday's own drop panel onto H0 (a next action) or a project (a `later` step), or pick its step or project on its page.

A task's is its due date (the task page labels the box "Tickler" while it's someday); a project's is `tickle_on` in its own table `project_tickles`, like `project_reviews`, set with the `tickler()` macro's box (⏳ on the project page's title line while someday; takes words, previews like Due only while focused, saves on change via `[data-submit]`). Until then it's out of the weekly review; from that day on it's back at the top of the Inbox (`db.tickled()`, ↩, counted in the Inbox dot) until you commit to it, give it a new date, clear the date, or drop it. Someday hides them too, until "Show tickled" beside Expand all (`?tickled=1`, `toggle_url(show, "tickled")`; only when something is tickled ahead); shown, a project's row says "until …". A project date set to today or earlier is flashed (back in the Inbox at once). A project leaving someday (or abandoned) loses its date. A task becoming someday drops a due date already come (`_fit_step()`), so it doesn't land straight back in the Inbox; one to come stays as its tickler.
- **Reference** (`/reference`, table `reference`, `REFERENCE_FIELDS`) is one flat list of title + notes: information with no action, kept here so it needn't live in another app. No projects, tags or folders (yet); search finds it.
  - Only material worth looking up goes here: given-up projects are abandoned (Done), not turned into reference, so Reference doesn't fill with dead items.
  - Adding an item opens its page, so its notes go in right away.
  - An item's page (`/reference/<id>`) has no separate list of its links: the notes editor shows them and opens them with ⌘/Ctrl-click (any `scheme://`, so `obsidian://` too). Deleting is a hard delete and returns to the list.
- **Reminders** push a task to the phone at a chosen time through ntfy, self-hosted on the VM (set up by `ntfy-setup.sh` in the home-server repo; tailnet only, no auth; the phone's ntfy app subscribes to `gtd`). They are rare, time-sensitive pings, separate from due dates: nothing links the two, and a repeat's next instance gets no reminder.
  - `tasks.remind_at` (UTC ISO, `db.iso()`) and `tasks.reminded_at` (set once sent). The task page's Remind box takes words (`dates.parse_when()`: `tomorrow 9am`, `fri 14:00`, `oct 30 at 5pm`, `in 2 hours`; a date alone means 9:00, a time alone the next one) and shows local `YYYY-MM-DD HH:MM` (`local_minute` filter), which it reads back unchanged. As you type, the hint beside it shows how it reads (`/parse/remind`, above); untouched, it shows "sent" or nothing. A new time already past is flashed and not set; the shown value saved unchanged is left alone, however old.
  - A row shows 🔔 (its time as the tooltip) while a reminder is still to come; the `.remind` slot is always rendered, like ↻.
  - With `NTFY_URL` set, a daemon thread in `app.py` (`reminder_loop()`, one per gunicorn worker, so one) runs `send_reminders()` on every minute: open tasks with `remind_at <= now` and no `reminded_at` (`db.due_reminders()`). A failed send stays unsent and is retried next minute, except a 4xx (not 429), which is logged and given up. Done and abandoned tasks never fire.
  - `ntfy()` publishes JSON to the server root (topic from `NTFY_URL`): title = task title; message = project (or H0 / Inbox) and due date, the first notes line, and "Late: was due …" when sent over `LATE` (2 min) after its time. With `GTD_URL`, a tap opens the task, and two ntfy `http` action buttons call the app straight from the notification: Done (`/tasks/<id>/complete` with `X-Requested-With: fetch`, 204) and Snooze 15m (`/tasks/<id>/snooze`, 204; `SNOOZE`).
  - Changing `remind_at` clears `reminded_at` (`update_task()`), so a new time (a snooze too) fires again.
- **Timer** (`/timer`) replaced a standalone time tracker on 2026-10-22. Every time entry belongs to a task.
  - Table `time_entries` (`task_id` → `tasks`, `ON DELETE CASCADE`; `start_time`, `end_time` as UTC ISO-8601 to the second, written by `db.iso()`). No `end_time` means running. A partial unique index allows only one running entry.
  - `now()` in `app.py` reads `app.config["NOW"]` (pinned in tests), like `today()`. Never call `datetime.now()` in a route. Forms show and take local time (`local_input()`).
  - `db.timer_start()` stops whatever is running first. `complete_task()` stops the task's timer.
  - ▶ on every open task row (`row()` macro, always visible, never hover-only) starts it. On the task page, ▶/■ and the time spent sit at the right of the project line above the title (`.task-timer`, an H0 or inbox task gets the line for it alone); while running, that total ticks (`data-seconds`, the clock JS in `static/app.js`). The running timer shows as a pill pinned to the bottom of the window on every page (task link, clock, ■ stop), so it never scrolls away; one clock script in `static/app.js` ticks both it and the task page's total. Stopped (■ anywhere), the pill stays for `STOPPED` (10 min) as `.running-timer.stopped`: the stretch's frozen time, the task link, ✓ (complete), ▶ (again) and × (`/timer/dismiss`, remembered in the session as `pill_dismissed`). `stopped_timer()` in `app.py` (from `db.timer_last()`) shows it only while that task is open and no timer runs.
  - The Timer page's start box matches an open task by title (case-insensitive), or captures what you typed to the inbox and times that, so everything timed is in the system.
  - Editing an entry saves only fields that differ from what the form showed, so untouched times keep their seconds. Setting an end on the running entry stops it.
  - The history has no visible Save: `static/app.js` submits an entry when focus leaves its row with a time changed (moving between its start and end doesn't), or on Enter. An end before the start isn't sent; the row gets `.bad` until fixed. A hidden Save stays first in the form so Enter saves rather than pressing ▶.
  - Totals: time spent on the task page; per project today and this week on the Timer page ("H0 · ground level", "Inbox (unprocessed)" for the rest), in two columns side by side (`db.week_totals()` from local midnight and from Monday); per step at the bottom of a project page (`db.step_totals()`, done and abandoned steps included, untimed ones left out; each label opens its task), folded to its total until "Show split" (`tally(fold=True)`, a `<details>`). All are the `tally()` macro (`_task.html`): a big total, then one accent bar per item, longest first.
## GTD rules encoded in the code

- **A task has a state and, inside a project or H0, a step.** There is no task "status".
  - `tasks.state` is `open | done | abandoned`; every open-task query says `state = 'open'` and never looks at `step` for that.
  - `tasks.step` is `next | waiting | later` for a project's task, `next | waiting | someday` for an H0 task, and `NULL` exactly for inbox items. `later` means a project step that isn't the next action yet. Beware SQL's `NULL`: `step != 'later'` skips every inbox item.
  - The schema enforces it: `CHECK ((step IS NULL) = (project_id IS NULL AND NOT ground))`, no `later` H0 task, no `someday` project task, and no H0 task in a project (the live DB was rebuilt for these on 2026-10-30, and for `someday` on 2026-10-31). `_fit_step()` (run by `add_task`/`update_task`) drops a step given to an inbox item; gives an H0 task `next` unless told or already `waiting` or `someday` (a `later` arriving is `next`); and takes a task joining a project out of H0 and makes it a `later` step unless a step is given or it was waiting (a `someday` given or held becomes `later`), so an H0 next action doesn't become the project's next by moving. `task_view()` drops the posted step when the project changed and the step select didn't, so a move from the task page lands the same way.
  - Writes reject unknown fields (`_insert` as well as `_update`), so a stray `status=` raises.
- **The inbox is not a step or a state.** It is every open task with neither a project nor H0, "ground level" (`tasks.ground`): `INBOX` in `db.py`, `db.inbox_tasks()`, and an `inbox` column on every `TASK_SELECT` row. Only H0 is a deliberate choice of no project; any other projectless task is an orphan, and orphans are the inbox.
  - Filing by drag: see "Moving tasks by drag" below; Inbox is one of its lists.
  - Completing an inbox item files it under H0 (`complete_task()` sets `ground` and step `next`), so done work and its time always have a home and the Timer shows no "(no project)" row; a repeat's next instance stays in the inbox. Abandoned ones are left as they are.
  - There is no Process page (removed 2026-10-27): the Inbox page is where items get dealt with (drag to file, ✓, or open one). Don't add a second page doing the same.
  - **Process** (the Inbox header's button; `dialog.process` in `inbox.html`, `static/process.js`) walks the inbox top item first, one question per screen, Allen's flowchart: Actionable? (no: Trash = abandon, Someday, Reference) → Part of a project? (yes: pick or ＋ New, named after the item, ›; then "Its next action?" → Make next or stays later) → Under two minutes? (Do it now: ✓) → Yours to do? (yes: When? → H0 next action; Delegate: Follow up when? → H0 waiting; both answered in the item's own Due box, optional). Picking an answer (Trash/Someday/Reference, the next-action Yes/No) only marks it (`aria-pressed`); nothing is filed until File, the last screen's primary button (Enter; disabled until a pick). ✓ Done is the one immediate answer. File posts to the existing routes in the background (`/tasks/move`, the task page's fetch save, complete, delete, make-next); the row leaves and the next item follows; at zero the page reloads. y / n answer, Enter files, ‹ goes back, Esc stops. `/inbox?process=1` opens it at once (the weekly review's inbox step links there; the flag is dropped from the URL). Clicking an Inbox row (title too) opens it at that item instead of the task page (a capture-phase listener in `process.js`, ahead of `app.js`'s row click); ⌘/Ctrl-click still opens the page, and after that item it carries on from the top. No skip: every item gets decided. Keep it a quiet overlay: the item, then under a thin rule one line with the question (body size, bold) and ghost answers; only a live File is filled, and the count, ‹ and × sit beside the title. Embedded, the item's fields have no box until hovered or focused.
    - The item is its own task page in an iframe (`/tasks/<id>?embed=1`; `embed` from the context processor), so it's clarified on the way: title, notes, due, repeats, remind, saving as on the page. Embedded, `base.html` hides the nav, bar and timer pill (CSS, `body.embed`) and adds `<base target="_top">`; `task.html` drops the project/step row, ▶, ✓ and ✕ (Process files it); `app.js` skips centering and the go-keys. Before any answer files the item, Process blurs the frame's field and awaits its `autosaved()` (`autosave.js`: title and notes saved, and app.js's `fieldsSaved`, the other fields' background save); a conflict stops it. A new project's name is read from the frame's title when asked.
  - The task page shows the step picker for open project and H0 tasks (H0: next, waiting, someday), not for an inbox item. `orphaned()` in `app.py` flashes when a task lands in the inbox.
- **H0 tasks are next actions, waiting or someday** (`step`): H0 next actions are on Next with the projects' (the H0 tab was merged into Next on 2026-10-31, once areas no longer set them apart); H0's waiting tasks are on Waiting, the delegated single actions no project needs; its someday tasks are on Someday, the single ideas not committed to.
  - **H0 tasks need no due date** (the always-dated rule of 2026-10-30 was dropped on 2026-10-31): undated ones fall in Next's No date band and aren't in its count. A someday one's date is its tickler (`_fit_step()` uses `today=` only for that).
  - H0 is the `h0` option in the `project_select()` macro, so choosing a project and choosing H0 are one decision. Its "＋ New…" option reveals a `new_project` box; `task_fields_from_form()` creates an active project from it and uses it, overriding the dropdown. A repeat rule doesn't exempt a task.
  - H0 next actions are also listed on the Horizons page's ground card (`db.h0_actions()`, `H0_NEXT`); their rows show an H0 tag where a project's link would be.
  - Next's add line preselects H0 in its project select, so a ground-level task needs no Inbox trip. The task form and the Next, calendar and Waiting add lines send a task with neither a project nor H0 (the blank `project…`) to the inbox.
  - The Next page's add line (`/next/add`, `add_next_action()` in `app.py`, shared with the calendar) adds a next action directly: a `later` step if its project already has one.
  - The Waiting page's add box (`/waiting/add`: title, project or H0, follow-up date) adds a `waiting` task; the Someday page's (`/someday/add`) adds an H0 someday task, or (kind project) a someday project.
- **Weekly review** (`/review`) is a checklist you finish, in Allen's order: get clear (collect loose ends, inbox to zero, mind sweep), get current (overdue, next actions, look back, look ahead, waiting, projects, checklists), get creative (someday / maybe, new ideas), then horizons.
  - Its steps are `REVIEW_STEPS` in `app.py`, one card each in `review.html`.
  - Look back lists tasks done in the last `LOOK_BACK` (14 days), a repeat once with its count (`db.done_since()`). Projects lists every active and waiting project, stalled (⚠) first, then least recently reviewed, each with its next action and a ✓ (`/projects/<id>/reviewed`); its count is how many weren't looked at in the last week (`unseen()`), as for someday. Checklists links Reference items holding a checklist. New ideas has the page's add line (Someday's, item or project), above the deck as on Horizons; `back()` keeps you on the review. A tick posts to `/review/<step>` (ticking again unticks) and is stored in `review_checks`, so a half-done review survives a closed tab.
  - One card shows at a time (a deck, `ol.deck`): `?step=`, else the first unticked. A rail of dots in the header (ticked, current, to do) links to each, between ‹ › buttons (`rel="prev|next"`): the `stepper()` macro in `_deck.html`, shared with Horizons. ← → follow those links (`static/app.js`, on any page that has them). Ticking moves on to the next unticked step; unticking stays. A step with something to count leads with it as a big number (✓ when zero), then a one-line hint. The inbox step's button opens the Inbox with Process running (`/inbox?process=1`).
  - Ticking the last step records the date in `reviews` (`db.complete_review()`), flashes "Weekly review completed on …" and clears the ticks. Past reviews show as a streak of the last 26 weeks (Monday-first squares, filled when reviewed; the date is the tooltip).
  - It lists next actions to scan, leaving out any due today or later (overdue ones stay), so the review can be finished.
  - Its someday step lists someday projects and H0 someday tasks together, never reviewed first, then the longest ago, leaving out any tickled to a later date (`db.someday_to_review()`), each with ✓ (`/projects/<id>/reviewed` or `/tasks/<id>/reviewed`, back to the review). The time is in tables of their own, `project_reviews` and `task_reviews` (no ALTER on the live DB), read as `reviewed_at` (with `tickle_on`) by `db.projects()`/`get_project()` and `db.someday_tasks()`. Someday's project rows show it faintly (`ago` filter: today, 3d ago, 2w ago, 4mo ago, never).
- **Project statuses:** `active | waiting | someday | done | abandoned`. As statuses, someday and waiting are projects' only (a task is waiting or someday by its step). 
  - A project page's status is one select (active, waiting, someday, done, abandoned) that saves on pick (`project_view()`, `PROJECT_STATUSES`). Picking abandoned (`db.abandon_project()`) gives a project up from any status: it and its open steps are abandoned with one shared `completed_at` (to the millisecond), its timer stopped, its time kept. It leaves every list and picker (`PROJECT_GROUPS` has no abandoned group; a task page of its step keeps it selectable through `project_select(keep=)`), and its page's select shows "abandoned".
  - Revive (Done's button, `/projects/<id>/revive`, or picking another status on its page; `db.revive_project()`) brings it back as someday, then the picked status, its steps that share that `completed_at` as `later` steps; one abandoned on its own before stays abandoned. Reviving (or adding) one step of an abandoned project also brings it back as someday (`_reopen_project()`).
  - A task page links up to its project (an H0 task has no such link) and can move the whole project to someday from there.
- **One next action per project.** `db.update_task`/`add_task` enforce it: when a project task becomes `next`, the project's other `next` tasks become `later`.
  - When a project's next action is finished, nothing is promoted automatically and nothing navigates: the project shows as stalled (⚠) until you pick one with "Make next" on its page.
  - ✓→ (on a project step's task page only; `/tasks/<id>/done-then-project`, `complete_then_project()` in `app.py`) completes the step and opens its project, so you can pick the next one right away. It's the plain ✓ plus a deliberate jump; a task without a project just stays on the page.
  - **`next` is always a conscious choice, never a default.** A step added on a project page defaults to `later` (its step picker preselects it), even when the project has no next action, and so does filing an inbox item. Only Make next, the step picker, or the Next page's add line (below) set `next`.
  - An active project with no `next` task is "stalled" (⚠): the `stalled` column of every project row (`PROJECT_SELECT` in `db.py`); templates read it, never recompute it.
  - Tasks of waiting and someday projects stay off Next Actions (`VISIBLE_NEXT`).
- **Waiting** (`/waiting`, `waiting.html`) holds waiting projects (`project_list()`, ▸ and Expand all, dragged to reorder via `/projects/order/waiting`), then waiting tasks as task rows: H0's first, then project steps (a waiting step of a someday or done project too).
- **No contexts.** They were removed on 2026-10-23: they were never used, and having to pick one slowed processing. Don't bring them back without being asked.
- **Areas (H2) are only notes on Horizons**, like goals: nothing links them to projects or tasks (removed 2026-10-30: filing every project under an area was friction). An area's page (`/horizons/<id>`) is title and notes, deletable. The live DB keeps an unused `projects.area_id` (nulled on deploy) and `horizons.archived_at`; harmless.
- **Next lists every next action** (`db.next_list()`, `NEXT`): H0's and active projects' (not waiting or someday projects'), repeats not yet due too, sorted by due date (undated last).
  - The rows fold into due bands (`banded()` in `_task.html`, `BANDS`, `soon()` and the `bands` filter in `app.py`), each a `<details>` with a count: Now (overdue + today) open; This week, Later and No date folded. Empty bands aren't shown. `static/app.js` remembers a band you click open or folded, per page (`localStorage`, `fold:<path>:<band>`); only clicks are saved, since a band that starts open fires `toggle` too.
  - Dates and ↻ show on hover (an overdue date always).
- **A task row's project link follows its title** (`.name` in `row()`), so it doesn't float alone in the right-hand column once dates hide; the title has `flex-basis: 0`, so a long one wraps instead of pushing the buttons onto a line of their own.
- **Recurring tasks** keep their step (or H0), except a next step comes back as later (below), but don't count until their due date: the weekly review and `db.next_actions()` use `VISIBLE_NEXT`.
- **The Next nav count** shows only tasks due today or overdue (`DUE_NEXT`), so undated tasks and future repeats aren't in the number.
  - `complete_task()` marks the task done and inserts the next instance. A repeating `next` step's instance is a `later` step, so the project stalls until you pick its next action; waiting steps and H0 tasks (next or waiting) keep theirs.
  - A repeat rule without a due date gets today as its due date.
- **Projects can't be marked done while they have open tasks.** Moving a project out of done clears its `completed_at`.
  - An open task joining a done project (filing, the dropdown, adding, reviving) reopens it as active (`_reopen_project()` in `add_task`/`update_task`/`revive_task`).
- **Only an empty project can be deleted** (no tasks at all, done and abandoned ones included; `db.project_deletable()`). The project page shows ✕ only then.
- **Deleting a task abandons it** (`db.abandon_task()`: state `abandoned`, `completed_at` set, its timer stopped, its time kept).
  - Revive (`/tasks/<id>/revive`, `db.revive_task()`) brings it back where it was: a later step of its project (reopening the project if it's done), an H0 task (next or waiting, as it was), or the inbox.
  - Deleting an abandoned task is a hard delete (its time too).
  - Completing an abandoned task does nothing. Search and suggestions include abandoned tasks with the done ones.
- **Horizons** live in one table keyed by `level`:
  - `purpose` and `vision` are single seeded notes that can't be deleted.
  - `goal` and `area` are lists of notes.
  - The Horizons page is a deck like the review (no ticks): one card per `HORIZON_STEPS` key (purpose, vision, goal, area, projects, ground: H5 down to H0), `?level=`, else purpose (H5); titles in `HORIZON_TITLES`. Purpose and vision cards autosave their notes; goal and area cards get the page's add line; deleting a goal or area returns to its card.

## Tests

Every change must be verified before it is called done:
1. For a change in behavior (a GTD rule, a route, a query, date math, JS behavior), write or extend a test that fails without the change, and watch it fail first.
2. Run the whole suite (`uv run pytest`; with template or JS changes, `uv run pytest -m ""`).
3. Click through the real app (`GTD dev`) for anything visual.

Keep the suite from piling up:
- Prefer extending the existing test for a feature over adding a new one.
- Looks (CSS, spacing, wording, icons, layout) get checked by eye, not by a new test; the crawl already checks every page renders and keeps the skeleton.
- A browser test only for JS behavior the Flask client can't see; anything checkable in the HTML goes in `test_app.py` (milliseconds, not a Chromium page).
- When a feature is removed or changed, delete or rewrite its tests; don't add "X is gone" tests for it.

Enforcement:
- Tests run in parallel with pytest-xdist (`-n auto` in `pyproject.toml`'s `addopts`): one process per core, each with its own Chromium and live server for the browser tests. `test_every_form_submits`, the slowest, is split into `SHARDS` parts so they run side by side. Tests mustn't share state across files or depend on order.
- A Claude Code Stop hook (`.claude/settings.json` → `.claude/hooks/run-tests.sh`) won't let a turn end while tests fail. It also runs the browser tests (in the same run) when `templates/` or `static/` have uncommitted changes. After a green run it stores a fingerprint of the working tree (`.git/tests-green`) and skips the tests on a turn that changed nothing since.
- `.githooks/pre-commit` refuses commits while tests fail. It also runs the browser tests (in the same run) when the commit touches `templates/` or `static/`. It is enabled per clone with `git config core.hooksPath .githooks`.

Layout (Flask test client, temporary DB):
- `tests/conftest.py` holds the fixtures:
  - `client` pins `TODAY = 2026-10-22` and makes Jinja undefined variables raise errors, so a template typo fails instead of rendering blank.
  - `conn` opens a second connection to the same file, so assertions can go straight to `db.*`.
  - `seed(c)` builds one of everything the UI can show (each task status, H0 next and waiting, repeats, waiting/someday/done projects, H0 someday tasks plain (reviewed), tickled to today and to later, a tickled someday project, a checklist in Reference, horizons). Its ids are deterministic.
  - New date-dependent behavior should be tested against the fixed date.
- `tests/test_app.py` holds the targeted tests: GTD rules, routes, recurrence, edge cases.
- `tests/test_browser.py` (marker `browser`, Playwright + Chromium, one live server per run on a random port, a freshly seeded DB per test) drives the JS: tick-off, search suggestions, theme toggle, capture dialog, dragging project steps and projects, the project rows' ▸ and Expand all, `/` and `f` keys, date picker, timer clock, timer entry autosave, the Markdown notes editor (rendering, saving, undo, toolbar, checklists), the Due, Repeats and Remind box previews, autosave and its conflict choices, the add line and "＋ New…" reveals, calendar day click and drag-to-reschedule, dragging rows of every task list onto projects and someday (and a someday task onto H0), the Inbox's Process overlay, a someday project's tickler box, and fails on any JS error. One-time setup: `uv run playwright install chromium`.
- `tests/test_crawl.py` holds the generic tests. They usually catch accidental bugs before anyone writes a targeted test for them:
  - Every link reachable from `/` must load.
  - Every form, with each submit button and each `<select>` option, must submit and land on a 200 page. Each submission gets a fresh copy of the seeded DB and sends its own page as the Referer.
  - Saving any edit page without changing anything must leave the record unchanged.
  - Task rows must match what the tick-off script expects.
  - When you add a page, field, state or step, add it to `seed()` so the crawler reaches it.
